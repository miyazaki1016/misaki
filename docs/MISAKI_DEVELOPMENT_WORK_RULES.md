# Misaki 開発運用ルール（正式版）

制定日：2026-10-23
適用範囲：Misaki の実装・調査・監査・検証・文書更新の**すべての作業**。チャットが変わっても引き継ぐ。
採用理由：作業途中で会話が中断しても、最後の確定状態をGitHubから復元できるようにするため。

## 必須の5段階

### 1. 作業開始時
- `docs/IMPLEMENTATION_OVERVIEW.md`（総覧）、`docs/MISAKI_CHAT_HANDOFF_20261021.md`、必要な設計正本・監査記録を**GitHubから再取得**し、作業対象のブランチ・HEAD・既存変更・未完了・安全上の制約を確認する。
- 記憶や直前の会話だけで「実装済み」「テスト済み」「main反映済み」を判断しない。
- どのコミットを基準に照合したかを明記する。古い固定コミットと最新HEADを混同しない。

### 2. 作業単位が一つ完了したら
- 実装・調査・検証の成果を、**作業したGitHubブランチ**に保存する。
- 実験コードは実験ブランチ、監査・全体引継ぎは監査ブランチで所在を整理し、重要な成果が別枝にあるときは正本から参照できるようにする。
- 保存できない場合は「GitHub未保存」と明示し、完了・引継ぎ済みと誤認させない。安全チェックの迂回は禁止。

### 3. 毎回必ず記録する項目
1. **目的・理由**：何をしたか、なぜ必要だったか。
2. **変更箇所**：リポジトリ、ブランチ、変更・新規ファイル、照合基点コミット。
3. **実施内容と検証**：実際に実行したコマンド/試験、成功・失敗・未実施。オフライン、CI、Preview、iPhone実機、本番は明確に区別し、実行していないテストにPASSをつけない。
4. **確定/未確定**：完了事項、未完了、既知の問題、安全ブロック、推定と実測の区別。
5. **次の一手**：次の担当が、どの枝・ファイルから何をすればよいか。
6. **保存証拠**：コミットSHA、保存先のパス、GitHub読戻し結果。

### 4. GitHub保存後に必ず再確認
- コミット成功の応答だけでは「保存検証完了」としない。
- 保存したファイルを**同じブランチのGitHubから読み直し**、期待したタイトル・対象・追記・重要な内容が実際に存在することを確認する。
- 最終コミットSHAと保存したブランチ/パスを報告する。
- 読戻しに失敗した場合は「コミット応答あり／GitHub読戻し未確認」と分ける。内容が異なれば完了扱いにしない。

### 5. 途中中断しても再開できる状態に
- 総覧／引継ぎの冒頭から**最新の作業記録・実験枝・次の手順**に到達できるようにする。進捗が分散したらリンク/索引を追記。
- 必ず「最後に確実に完了した工程」と「これから実施する工程」を分ける。
- 新しいソラは最初にGitHubを再確認し、ユーザーへ同じ説明を求めずに再開する。

## 作業終了報告の共通様式

- **目的・実施したこと：**
- **変更先：** `branch` / `path` / 基準コミット
- **検証：** 実行済み（結果）・未実行（理由）
- **完了：** 確認できた事項
- **未完了・懸念：** ブロック、追加試験など
- **GitHub保存：** commit SHA／読み直しの結果
- **次の作業：** 開始する場所と手順

## 既存の安全規則は維持
- この運用ルールは、既存の**本番・main・Supabaseの無断変更禁止**、Forgetやlegacy BLOCKEDの扱い、ユーザーの承認要件を緩和しない。
- チャットからの「りょ」は、直前に合意済みの**安全な作業の続行**を意味し、本番反映や課金API実験の無条件承認にはならない。
- 実験の合成データの文字数・バイト数を、実際のGemini請求額や品質改善と取り違えない。
