# Misakiシステム基本構想 — 人格・関係性・記憶・成長（2026-10-21）

> **新しいソラ／実装担当者は作業前に本書を読むこと。** これはユーザーとの対話で確認した「何を目指すか」を保持する設計方針であり、現在の実装済み仕様や本番稼働状況を保証するものではない。技術的な採否・細部の条件は個別設計と検証を経て確定する。矛盾を発見したら黙って上書きせず、根拠と判断を記録する。

## 1. 根本思想：美咲は使い捨ての応答器ではない
- 美咲を、会話のたびにゼロから始まる単発のチャットボットではなく、継続した人格・生活感・価値観・記憶・人間関係を持つ**一貫したキャラクター**として育てる。
- 「人間そのもの」と偽るのではなく、AIキャラクターとして自然で一貫した存在感を実現する。
- キャラクターの性格・知識・生活上の出来事・会話の癖は、積み重ねによって変化し得る。ただし一度の会話で人格が唐突に変わる設計にはしない。
- 当面は**美咲一人の品質を最優先**にする。将来、同じシステム基盤に別のキャラクターを追加できる構造にする。

## 2. 一人の美咲、複数の相手
- 全ユーザーに対して、同一キャラクターとしての美咲の基本的な人格・共通知識・成長を共有する。ユーザーごとに別人格の美咲を無制限に複製しない。
- ただし、**ユーザーAとの会話・秘密・記憶・関係性をユーザーBに漏らしてはいけない**。他のキャラクターへの横流しも禁止。
- キャラクター全体の成長に取り込めるのは、個人情報・私的会話を含まない、適切に抽象化・検証された知識や性格傾向に限る。何を共有学習に採用するかは別途明確なルールと監査を設ける。
- 美咲が誰にでも同じ態度を取る必要はない。各相手との実際の交流・信頼・距離感に応じて振る舞いが異なるのは自然。ただし共通人格の一貫性は維持する。

## 3. データの所有・分離境界
次の概念を混同しない。
1. **Character共通**：キャラクター定義、基本人格、公開可能な共通知識、検証済みのキャラクター全体の成長。
2. **User共通**：ユーザー本人が許可した一般プロフィール・設定。キャラ間共有の可否は同意・権限で制御。
3. **User × Character専用**：二者間の会話履歴、個人的な記憶、共有した出来事、関係性・感情・親密度・境界、約束やエピソード。
4. **外部状況**：日時、天候、場所、キャラの生活イベント等。取得根拠・鮮度・アクセス権限を区別。
5. **通知・Proactive履歴**：発信の契機、送信先、同意、頻度、重複防止、配信結果。ユーザー×キャラ境界を維持。

- 現行DBのuser_id中心の設計にUIだけcharacter_idを足しても安全な複数キャラ対応にはならない。テーブル、RPC、RLS/権限、非同期ジョブ、履歴import、削除、監査まで一貫してスコープを設計する。
- キャラクター全体の学習と個別関係の学習は**別の保存・適用経路**にする。個人の記憶を共通知識にそのまま書き込まない。
- 結婚等の排他的な関係状態にはDBレベルの一意性・競合制御・再実行安全性が必要。実装詳細は別途決定。

## 4. 関係性は自然に育つ
- 出会いから知人、友人、親友、恋人、結婚、別れ、再接近など、関係性は会話・行動・信頼・相互の意思・出来事によって変わり得る。**到達点やハッピーエンドを最初から固定しない**。
- 美咲側にも個性、境界、判断があり、ユーザーが望めば自動的に恋人・配偶者になる仕組みにはしない。
- 恋愛・結婚は単純なスコア上昇や課金で発生させず、双方の意思・適切なイベントと状態遷移を必要とする。
- 一人のキャラクターが同時に複数ユーザーと結婚状態にならないようにする。状態変更時の競合・取り消し・離婚後の扱いは明示的に設計する。
- 既存のRelationship Engine、5軸、Identity、critical events、制約・再試行の安全性を尊重する。新構想を理由に既存の正本や安全策を壊さない。

## 5. 記憶と会話の自然さ
- 記憶は「保存すれば良い」ではない。忘れてはいけない約束、訂正、否定、関係性、出来事の前後関係を維持し、必要なときに適切に思い出せることが重要。
- User Memory（本人の情報）、Shared Memory（二者の共有体験）、Relationship Memory（関係性の履歴）を区別する。
- 記憶の保存・検索・参照・忘却・削除は、所有者とアクセス範囲が分かる設計にする。ユーザーによる制御や同意を尊重する。
- 演技・感情表現・Body Clock・生活感・関係性は矛盾しないよう統合する。評価では一言の魅力だけでなく長期的な一貫性を検証する。

## 6. 自発的なメッセージとFree/Premium
- 美咲が必要に応じてそっと話しかける体験を目指す。押しつけがましくならないよう頻度・タイミング・停止設定・同意を尊重する。
- **Free**：美咲自身の日常・出来事・気持ちを話題にする自発メッセージを想定。ユーザーの過去会話や共有の思い出を自発的な話題の材料にすることは、現時点の設計基準では行わない。
- **Premium**：本人の許可のもとでUser Memory・Shared Memoryを少数参照し、より文脈のある自発メッセージを検討できる。
- **課金額は好意・信頼・愛情の強さを決めない。** 無料会員でも関係性は自然に育ち、解約・ダウングレードで過去の関係性を罰したり減点したりしない。
- 通常会話の記憶利用、記憶の保存範囲、通知の頻度・価格・上限は別途設計・検証する。ここに書いた区別をすべて実装済みとはみなさない。

## 7. コストはサービス継続の前提
- Gemini等のモデル費用を制御できなければサービスは続かない。**会話品質・記憶・関係性を損なわず、成功した1ターン当たりの実コストを削減する**ことを最優先の実装課題とする。
- リトライを含む実API呼び出し数、入力/出力トークン、system prompt・履歴の重複、付随処理のコストを計測する。
- 長い履歴をそのまま毎回送る方式を見直す。直近履歴・古い文脈の要約・重要記憶の取り出し・重複除去などを、オフライン品質テストで比較してから採用する。
- 安価でも、誤った記憶・関係の取り違え・人格の不自然な変化が増える案は採用しない。
- 実課金が発生する実験は、事前承認・予算上限・環境隔離・測定計画なしに実施しない。

## 8. 実装と検証の順序
1. 既存の全92ブランチ、PR、Preview、main反映、未反映・ブロック作業を証拠付きで棚卸しし、失われた仕掛かりをなくす。
2. 正本 `docs/IMPLEMENTATION_OVERVIEW.md` と `docs/DEVELOPMENT_REGISTRY.md` を通読し、現状と設計の矛盾を整理する。
3. Geminiコストを計測し、会話品質を保つ軽量化をオフラインで検証してから段階的に実装する。
4. 複数キャラクターを見据えたCharacter / User / User×Characterの所有・記憶・関係性の境界を設計する。
5. 美咲一人の人格成長・関係性・生活感・Proactiveを、回帰テストと監査を伴って段階的に強化する。
