## 1. 調律の適用範囲と「悪い適用」の影響範囲

調律設定が美咲共通の場合、本番適用した版が悪ければ影響が全ユーザーに一斉に出ます。下書き／適用の分離とロールバックだけでは不十分で、次を決めてください。

- 適用を段階化できるか（例：試験用の限定範囲 → 全体）。できない場合、ロールバックは「最後の正常版へ戻す」手順を実際にテストで検証し、適用と同じ速さで戻せることを合格条件にする
- 適用は本番変更として扱い、適用者・変更理由・版の記録を必須にする（文書の「バージョン・作成者・変更理由」と整合）

## 2. 調律の変更履歴そのものも仮名化・最小化の対象にする

共通材料契約では「生IDや生会話を監査ログへ無制限に残さない」とありますが、調律側の履歴（誰が・いつ・何を変えたか）も同じ扱いにしてください。設定値の履歴は運用者の行動記録であり、選別の監査エンベロープと同じく、保存するなら仮名化と保存期間の設計が先、が原則です。あわせて、調律値そのものにユーザーやキャラを特定できる内容（特定ユーザー向けの例外設定など）を持たせないことを、契約側の禁止事項として明記してください。

## 3. 「適用後の新しい会話ターンだけに効かせる」の定義を固定する

版の切り替わり目が曖昧だと、同じ会話の中で口調が不連続に変わり、後から「どの版で生成されたか」を追えなくなります。

- どちらの場合も、各ターンの生成に使った調律の版を（仮名化した形で）記録し、答え合わせができるようにする

## 1. 最小共通契約（#199→#220→#194）

#194 担当の最小契約案（スコープ付き受け渡しの読み取り専用利用、調律は別オブジェクト、版の固定とターン単位の紐付け、A/B の軸分離）を支持します。追加で1点：**制約は全工程で「保持」が原則**とし、各段が制約を黙って落としたり弱めたりしないことを契約に明記してください。未知の schemaVersion・未検証スコープに対する fail-closed は入口だけでなく、#220・#194 の各受け渡し点でも同じに適用します。

## 2. 発話意図の責任と Gemini の裁量境界

境界は「Gemini は、選別済み材料と発話意図に**含まれない事実・評価・約束を新たに導入しない**」と定義するのが検証可能でよいと考えます。語順や言い回しの選択といった表現上の裁量は残りますが、それは意図の変更ではなく言語化の範囲であり、残余のリスクは次の送信前検査で受ける、という整理です。

## 3. 送信前検査の責任者とフォールバック（最重要）

- **検査は生成したモデル自身に自己採点させない。** 同一モデル・同一経路の自己評価は、誤りを相関して見逃します。
- **決定的に判定できる部分は機械的に検査する**：出力に含まれる固有名詞・日付・数値・約束表現が、選別済み材料の範囲内にあること。禁止事項への抵触。他ユーザー／他キャラの材料の混入痕跡。
- 意味的な検査（ニュアンスの逸脱など）を別モデルやヒューリスティクスで行う場合は「保証ではなく信号」として扱い、判定結果を記録に残す。
- **不一致時の動作を先に固定する**：検査に落ちた文章は送らない（fail-closed）。再生成は制約を強めて回数上限つき、それでも落ちれば安全な定型応答に落とす。検査側が文章を勝手に書き換えて通すことはしない。
- 検査結果は既存の監査の枠組み（snapshotId・選別ルール版・調律版・promptVersion）に紐付け、「何を根拠に・どの版で生成し・検査をどう通ったか」を後から追えるようにする。

隔離モードの要件（本番の記憶・感情・関係性・イベントを更新しない）に加え、試し会話の記録が本番の監査ログと混ざらないよう、試行であることを記録上も区別してください。本番適用は所有者の明示操作のみ・版履歴とロールバック必須、調律版は会話セッション開始時に固定、という既合意の線はそのまま維持で問題ありません。
