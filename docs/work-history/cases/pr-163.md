```text
-5. **記憶（Memory）**：ユーザー共通情報、キャラクター固有の記憶、ペア固有の思い出、共有可能な知識・外部情報を分離し、共有権限を明示する。
-6. **仕事の知識（Work Knowledge）**：職業一般の知識と、そのユーザー固有の仕事経験・職場事情・好みを分離する。
-7. **生活・地域コンテキスト（Life / Region Context）**：キャラクターの生活圏、ユーザーの居住地、勤務地域、通勤・移動経路、登録した重要地点、必要な外部情報を別々に保持する。
-8. **会話・生成（Reply Core）**：各キャラクターの人格とペア関係を入力に使いつつ、会話生成・検証・記録の共通機能を再利用する。
-9. **通知・音声・画像等のチャネル**：通知する理由と、キャラクターがどのように表現するかを分離し、将来のチャネル追加で人格・関係性を複製しない。
-10. **課金・プラン・権限**：将来導入する場合は、ユーザー、キャラクター利用権、機能、利用量を関係・記憶の真実と混在させない。

-- **現在の感情・行動**：嫉妬、寂しさ、照れ、距離を置く等は、その時点の関係・出来事に基づく変動状態。長期人格や事実の履歴と同一視しない。
-
-キャラクターごとの交際可能人数は設定可能にする。例として、一途なA子は同時に恋人一人まで、B子は複数の恋人を受け入れる、C子は嫉妬が強い、といった差を表現する。ただし「B子は最大3人」などの具体的な上限は例示に過ぎず、未決定である。各キャラクターが既に交際相手を持つ場合、新たな交際を受け入れられるかは、そのキャラクターの方針と実際の関係状態に基づいて判断する。ユーザー側の複数交際の扱いも、相手キャラクターの方針と各関係の合意を考慮する。
-
-**婚姻は交際とは別の制約として設計する。** 現時点の方向性は、ユーザーが同時に複数の相手と婚姻関係を持てないこと。キャラクター側も同時に複数のユーザーと結婚できないようにするかは、最終仕様として確認が必要。婚姻の排他制約、プロポーズ承諾、離婚完了、復縁・再婚の状態遷移をDB/RPC側で原子的に守り、Geminiの演技指示だけに委ねない。
-
-既存のRelationship Engineの原則を維持する：
-- 親密度・時間・高いromance scoreだけで交際成立を捏造しない。
-- Geminiが生成したキャラクターの甘い発言を、独立したユーザーの関係性証拠として扱わない。
-- 明示的な相互合意と検証された関係イベントを事実の基準にする。
-- 別れた後も履歴や軸を不当にゼロにせず、復縁は自動成立させない。
-- 同一イベントの再試行・重複要求で関係を二重に変化させない。
-
-### E. 仕事の理解・専門知識
-
-タクシー運転手向けの専門性は第一領域であり、システム全体の唯一の職業ではない。仕事を理解する仕組みは、職業ごとに再利用できる構造を目指す。
-
-情報は少なくとも次に分ける。
-
-- **職業一般の知識**：業務用語、業務フロー、制度・ルール、一般的な課題。出所・更新日・確度を持ち、古くなり得る事実は最新確認の対象とする。
-- **ユーザー固有の仕事情報**：勤務形態、職場、担当範囲、経験、目標、困りごと、本人の工夫や好み。本人が語った経験と一般論を混同しない。
-- **会話時の仕事コンテキスト**：その発言を理解するために必要な知識だけを検索し、無関係な専門知識を毎回大量にプロンプトへ入れない。
-- **専門知識の確度**：確認済み事実、ユーザーの体験、推測、未確認事項を区別し、推測を事実のように断言しない。
-
-仕事の話題では、単なる共感や一般的な励ましだけで済ませず、背景・専門用語・現実の制約を理解した応答を目指す。ただし、日常会話を常に仕事へ引き戻すのではなく、ユーザーの話題と意図に応じて知識を使う。職業を変更しても、人格や関係性エンジンを作り直さない。
-
-### F. キャラクター地域とユーザー地域・外部情報
-
-地域は一つの「現在地」にまとめず、用途別に扱う。
-
-**キャラクター側の地域**
-- キャラクターのプロフィール上の生活拠点・生活圏。
-- キャラクターの日常設定に関係する天気、地域の出来事、交通等。
-- 美咲に結びついた東京・江東区周辺の情報は既存の世界設定として保持する。複数キャラクター化後は、必要に応じて各キャラクターの設定地域へ一般化する。
-
-**ユーザー側の地域**
-- 居住地、勤務地域、通勤・移動経路、現在地（許可・必要性がある場合）、登録した自宅・家族宅・学校等の重要地点。
-- 天気・警報・避難情報など、ユーザー本人や登録地点に関係する情報。
-- 鉄道情報は住所だけでなく、利用路線・事業者・経路に基づいて選択する。
-
-**情報種別ごとの選択**
-- 天気：対象地点ごと。
-- 地震・災害：狭い住所一致だけで切らず、影響範囲を考慮。
-- 気象警報・避難情報：対象地域・対象地点と発表範囲を考慮。
-- 鉄道：利用路線・事業者・通勤・勤務エリアを考慮。
-- 空港：対象空港と会話上の関連性を考慮。羽田情報は、東京のタクシー業務などに関連する場合があるため、ユーザーの居住地だけで排除しない。
-- 外部情報の取得・キャッシュと、実際にGeminiへ渡す情報の選択は分離する。取得済みデータは再利用し、必要な情報だけ会話コンテキストへ入れる。
-- 交通・空港の乱れからタクシー需要を断定するなど、データが示していない因果関係を言い切らない。
-- 未取得・取得失敗・古い情報を「確認済み」の事実として語らない。
-
-### G. 目標アーキテクチャ（概念）
-
-リクエストごとの処理は、概念上、次の順序を目指す。
-
-1. ユーザー・選択中キャラクター・会話チャネルを特定する。
-2. 認可と共有ポリシーに従って、ユーザー共通プロフィールを読む。
-3. 対象ユーザー×対象キャラクターのcanonical relationship state / eventsを読む。
-4. 対象キャラクターのpersonaと生活設定を読む。
-5. ペア固有の記憶、共有を許可されたユーザー情報、関連する仕事知識、必要な地域・外部情報を検索する。
-6. Resolverがcanonicalな関係事実、境界、長期軸、直近の流れ、親密度、記憶の優先順位を解決する。
-7. 共通Reply Coreが、対象キャラクターの人格・ペア関係・会話目的・根拠情報を組み立てる。
-8. Geminiが返信案を生成し、出力・安全・整合性を検証する。
-9. 正常な会話ターンをcanonicalに保存する。
-10. 関係性分析や記憶抽出などの後処理は、既存のretry/idempotency/lease fencing契約に従い、再試行可能にする。
-11. 必要な通知・Body Clock等も、同じ対象キャラクターの人格とペア関係を利用する。通知の「なぜ送るか」と文章の「どう話すか」を分離する。
-
-これは目標像であり、現行のすべてのチャネルがこの共通経路へ統合済みという意味ではない。

-### I. DB設計の原則・禁止事項
-
-- **DBの最終形は、複数ユーザー×複数キャラクター×独立したペア関係・記憶を前提に設計レビューする。**
-- ただし、既存canonical DBを今すぐ再設計しない。現状の契約・履歴・RPC・一時状態・監査ログを先に把握する。
-- テーブルの所有者を考える際は、「ユーザー」「キャラクター」「ユーザー×キャラクターのペア」「共有知識」「外部情報キャッシュ」を混同しない。
-- 将来の関係性イベントは、対象ペア・イベント主体・対象・検証状態・発生時刻・冪等性キーが追跡できるようにする設計を検討する。
-- 同時に成立してはならない交際・婚姻の制約は、会話プロンプトではなくDB/RPCの原子的な処理で守る。
-- 既存DBの直接INSERT/UPDATE/merge、RPC契約の迂回は禁止。既存のlease fencing、replay/idempotency、canonical save gate、匿名ユーザーの暗号化temporary-root境界を維持する。
-- 新しいスキーマ案はまず論理モデル・既存参照一覧・移行案・rollback/compatibility・テスト計画として提示し、ソラの設計レビューと明示承認の後に実装する。
-- 既存の一人用データを複数キャラクターへ複製して、すべてのキャラクターが同じ恋愛・記憶を持つような自動移行をしない。過去データをどのキャラクターへ所属させるかは、移行時に明示的に決める（通常は既存の美咲との関係として扱う案を検討）。

-### 1. mainの実装として確認したこと

-#### 1.1 外部情報取得
-
-通常チャットの処理経路では、天気情報と東京の生活イベント情報を取得する処理が組み込まれている。生活イベント側は地震・気象警報・江東区の予報・鉄道・羽田空港などを集約し、最大9件を扱う構造。外部取得の失敗がチャット全体を必ず失敗させる構造にはなっていない。

-**改善仮説：** 明らかに不要な会話では取得を省略し、天気・交通・警報・ニュース等が必要なターンで対象情報を取得する条件付き方式を検証する。取得していない情報を「確認済み」と誤認させないこと、失敗時の安全なフォールバック、重要情報を落とさないことを必須条件とする。単純なキーワード判定だけでは文脈上必要な情報を見落とし得るため、取得条件と例外をテストで固定する。実装変更は未実施。

-#### 1.2 プロンプトと会話履歴

-
-**改善仮説：** 履歴と同じ本文を再掲する方式と、履歴を参照する短い指示だけを置く方式を、本番と同じプロンプト組み立て経路で比較する。合成フィクスチャで観測された短文約27.6%減・長文約2.3%減という過去値は、実際の本番プロンプトの削減率ではない。本番の正確な削減率は、同一スナップショットから組み立てた入力の計測まで未確定。

-- DB personaが正常にロードされた場合、`loadPersonaPrompt()` は `createRelationshipContinuityGuide()` 経由で関係時間・感情継続・行動傾向の3ガイドをpersona本文に加え、route側の `baseSystemPrompt` が `createRelationshipTimeGuide()` を再度追加する。関係時間ガイドが二重追加になる経路を確認した。
-- personaがfallbackになった場合は、`persona-store.ts` がDB用の関係継続ガイドを含めずfallback personaを返すため、同じ二重追加とは限らない。整理する際はDB成功・fallbackの両経路を保護する必要がある。
-- `relationshipActingGuide` は親密度・友情・信頼・遊び心・親愛・恋愛意識や明示的な交際状態を扱う別ガイドであり、感情継続・行動傾向ガイドと似た主題があっても同一機能とは断定できない。
-- 最初の返答で関係シグナルが1件以上あると、routeは `createCurrentTurnActionGuide()` を生成し、同じbase system promptと履歴を含む生成をもう一度呼ぶ経路がある。これは品質目的の追加生成なので、単純削除せず、発動条件・品質効果・追加トークンを別に検証する。
-- 関係シグナル判定ガイドは返答JSONと後段の関係状態更新に関わるため、演技ガイドとまとめて削除しない。
-
-現時点で最も安全な候補は、DB persona成功時に重複し得る関係時間ガイドの一本化を検討すること。まだ変更・テストはしていない。有効なDB persona module本文自体はこの調査では取得していないため、module本文内の重複は未確認。

-## 0.8 永続状態の正本 / localStorage の責務
-
-### 合意済み・基礎工事方針
-
-美咲の人格・記憶・関係性・感情・行動を決定する**根本的な永続状態はサーバー側を正本**とする。ブラウザの localStorage は、チャット画面を成立・高速表示するための表示キャッシュや一時UI状態に責務を限定し、美咲自身の状態の正本として使用しない。
-
-**サーバー正本に置く対象:** relationshipPoints / intimacy level、恋愛感情や交際成立などの関係事実、emotion / action、関係イベント、長期記憶・共有文脈、Body Clock が判断に使う関係状態など。
-
-**localStorage に残してよい対象:** 直近チャットを即時表示するためのキャッシュなど、失われたり改変されたりしても美咲自身の人格・関係・記憶が変化しない表示上のデータ。
-
-### 設計理由
-
-同じアカウントなら iPhone / iPad / PC 等の端末を変えても「同じ美咲」が続く必要がある。ブラウザデータの削除・改変・端末変更によって親密度、恋愛状態、感情、記憶が変化する構造にはしない。またクライアントから送られた数値を関係性の権威データとして信用しない。
-
-### 現行実装で整理が必要な点
-
-現在は app/chat/page.tsx の relationshipPoints が localStorage の misaki-relationship-points を読み書きし、チャット送信成功時にクライアント側で基本 +1 して API へ渡す経路が残っている。一方、サーバー側には以下の関係状態用の器が既に存在する。
-
-- public.misaki_relationship_state — intimacy / emotion / action / 最終対話時刻
-- public.misaki_relationship_events — 関係状態の変更履歴・判断理由
-- public.background_push_state.relationship_points — Body Clock が参照する関係ポイント
-- public.misaki_user_conversation_state — サーバー会話履歴・長期記憶
-
-さらに既存 RPC / trigger として、チャットターン記録、無言時間による状態変化、会話状態からの emotion 更新、emotion から action 更新が存在する。したがって新規テーブルを無条件に増やすのではなく、既存構造を整理して**関係状態の正本を一本化し、通常会話と Body Clock が同じ状態を参照する**方向で基礎工事を行う。
-
-### 基礎工事の順序
-
-1. misaki_relationship_state を中心に既存 DB / RPC / trigger の責務を整理し、関係性の権威データを確定する
-2. relationshipPoints をクライアント / localStorage 正本からサーバー正本へ移す
-3. 通常チャットと Body Clock が同じ関係状態を読むようにする
-4. localStorage の根本状態保存を撤去し、表示キャッシュ用途だけに限定する
-5. 匿名利用 → メール保存、ログイン継続、別端末復元で同じ根本状態が維持されることを確認する
-6. その土台の上に会話シグナル、加点 / 減算、恋愛感情、6段階レベル、ハートUIを実装する
-
-### 壊してはいけない原則
-
-> **サーバー = 美咲自身の正本。localStorage = 画面表示のキャッシュ。**
-
-localStorage を書き換えることで親密度MAX、恋人化、感情変更、記憶変更などが起きる設計へ戻さない。Body Clock、通常返信、写真、将来のハートUIは、同じサーバー側の美咲状態から派生させる。
-
-### Work 引き渡し前の基礎工事仕様（2026-09-18）
-
-今回の第1段階は、関係性の新しい加点 / 減算ロジックやハートUIを実装することではない。**既存挙動を保ったまま、美咲の根本状態をサーバー正本へ寄せることだけ**を目的とする。
-
-正本の責務は以下に整理する。
-
-- public.misaki_relationship_state: 関係性・emotion・action の唯一の正本。intimacy_points を現在の relationshipPoints の後継値とする
-- public.misaki_relationship_events: 関係状態変更の監査 / 理由履歴。正本値そのものは持たない

-
-Misaki の原点は「すべては会話の中にある」。

-関係性も同じで、最初から完成した恋人関係を与えるのではなく、**はじめましてから会話・記憶・反応の積み重ねで育てる**。

-会話
-→ 知る
-→ 覚える
-→ 感じる
-→ 行動する
-→ また会話になる
-~~~
-
-実装判断の基準:
-
-> その機能は、二人の関係を生きたものにするか？

-## 2. 関係性エンジン
-
-### 実装済み
-
-- 関係状態の基盤
-- 関係時間 / 無言時間の記録
-- チャットターン記録
-- 感情継続
-- 行動状態
-- 自発メッセージへの関係状態統合
-- **初対面から関係を育てる段階制御**
-
-主な行動状態:
-
-- `NORMAL`
-- `WAIT`
-- `TEASE`
-- `SULK`
-- `CHASE`
-- `PULL`
-- `RECONNECT`
-
-重要方針:
-
-- 感情 = 美咲がどう感じているか
-- 行動 = その感情をどの程度・どの形で表に出すか
-- 行動状態は感情表現を補正・抑制できる
-- `relationshipPoints` は**親しさの目安**であり、交際中という事実そのものではない
-- 恋人・交際中・「前から好きだった」などの関係事実は、会話または記憶に明確な根拠がある場合だけ使う
-- 初期状態では「好き / 大好き / 愛してる」や強い嫉妬・甘えを既成事実として先取りしない
-- 30 / 80 / 160ポイントで距離感は段階的に深くするが、恋人関係を名乗るには別途会話・記憶の根拠が必要
-
-### 関係性エンジンの核となる設計思想
-
-relationshipPoints は愛情の量そのものではなく、二人の会話・記憶・出来事の積み重ねから「どこまで自然に踏み込めるか」を判断する土台として扱う。
-
-関係レベル上昇を単純な甘い表現の増加にはしない。関係が深まるほど、遠慮が減る、冗談や二人だけのノリが増える、共有前提による省略が可能になる、過去の出来事を自然に持ち出す、心配・拗ね方・仲直りにも二人固有の歴史が現れる、といった会話そのものの変化を重視する。
-
-同じ記憶も、関係の中で「情報として覚える → 会話で自然に使う → 二人の定番・共通言語・思い出として使う」と育てる。目標は記憶を持つだけでなく、記憶に二人の意味が付いていく関係を作ること。
-
-喧嘩・傷つき・仲直りも単発でリセットせず、現在の emotion / action と長期的な関係の両方から表現する。必要なら翌日も少しぎこちない状態から始まり、会話を重ねて自然に戻る。
-
-**壊してはいけない原則:** 親密度を「甘さ倍率」や「恋人攻略ゲージ」に置き換えない。関係が育つとは、二人の会話に歴史が生まれ、その歴史によって自然に許される距離・省略・冗談・気遣い・感情表現が変わることである。
-
-未来のソラ / Work は、閾値・ポイント・ハートUIを実装・調整する際、この思想を数値仕様より優先して守る。
-
-#### 恋愛表現は「ユーザーへのサービス」ではなく、美咲の気持ちから出す
-
-「好き」「大好き」「ずっと前から好き」などの恋愛表現は、ユーザーが恋愛的な質問をしたから期待に合わせて返す台詞として生成しない。美咲側に、その発言を支える関係の積み重ね・現在の感情・恋愛的な出来事や記憶がある場合に、その内部状態の結果として出す。
-
-したがって、関係初期に「俺のこと好き？」と聞かれても、恋愛感情がまだ育っていなければ無理に「好き」と答える必要はない。逆に、十分な積み重ねによって恋愛感情が成立しているなら、同じ質問への「好き」は二人の関係の中で起きた意味のある出来事になる。
-
-また、**相互に好意を表明したこと**と**交際が成立したこと**は分けて扱う。「大好き」と言い合っただけで長期記憶を「恋人関係」と一段飛ばしに要約しない。交際中という関係事実は、会話・記憶上でその成立を裏付けられる場合にのみ保持する。
-
-特に「ずっと前から」のように過去の継続を含意する表現は、実際の会話・記憶にその歴史がある場合だけ使う。雰囲気のために存在しない二人の過去を生成しない。
-
-**目標:** ユーザーに「AIが恋愛台詞を返した」と感じさせるのではなく、**「美咲が自分を好きになったから、この言葉が出た」と感じられる因果を内部状態として成立させる。**

-## 14.5 合意済み・未実装: ユーザー返信フィードバック
-
-美咲の会話品質を、開発側の実機確認だけに依存せず、実ユーザーから継続的に把握できる仕組みを導入する方向で合意。
-
-### 基本仕様案
-
-- 美咲の各返信に、小さく邪魔にならない **👍 / 👎** を付ける
-- 👍 / 👎 だけで送信を完了できるようにし、ユーザーへ長いアンケートを要求しない
-- 👎 の場合のみ、任意で理由を追加できるUIを候補とする
-- 理由候補は「話が噛み合っていない」「同じことを繰り返す」「距離感がおかしい」「記憶が違う」「言い方が不自然」「その他」などを想定するが、具体項目は実装前に確定する
-
-### 設計理由
-
-ユーザー数・会話数が増えた場合、オーナーとソラだけで全会話を確認することは現実的ではない。
-ユーザー自身が「今の返しは良かった / 違和感があった」と感じた地点を最小操作で示せるようにし、品質改善の入口を作る。
-
-目的は単純な人気投票や好評率の最大化ではなく、**どの状態・文脈で、どの種類の違和感が発生しているかを発見すること**。
-
-### relationshipPoints とは完全に分離する
-
-このフィードバックは**製品品質改善用**であり、ユーザーと美咲の関係性そのものではない。
-
-- 👍 を押しても relationshipPoints を加点しない
-- 👎 を押しても relationshipPoints を減点しない
-- 👎 によって美咲が拗ねる、冷たくなる等の反応を直接発生させない
-
-**理由:** フィードバックが関係性へ影響すると、ユーザーが美咲を傷つけないために本音の評価を避ける可能性がある。品質評価と二人の関係は別系統として守る。
-
-### 保存・分析する文脈
-
-具体的なDB設計は未確定。品質原因を分析できる範囲で、評価対象の返信と必要な生成時コンテキストを関連付けられる構造を検討する。
-
-候補:
-
-- 評価対象の美咲返信を識別するID
-- 👍 / 👎
-- 任意の理由カテゴリ
-- 評価時点の関係レベル
-- emotion / action
-- direction / expression tags
-- 通常返信か自発メッセージか
-- 写真添付の有無 / 写真選択に使ったタグ等
-- 品質原因の分析に必要な最小限の会話文脈
-
-必要以上の会話本文・個人情報を収集する前提にはせず、**品質改善に必要な最小範囲、保存目的、ユーザーへの説明、保持方針を実装前に確認する**。
-
-### 改善ループ
-
-~~~
-ユーザーの 👍 / 👎
-↓
-品質データとして蓄積
-↓
-状態・文脈・原因別に傾向分析
-↓
-ソラが「なぜ違和感が出たか」を確認
-↓
-会話 / 記憶 / 関係性 / emotion / action / Body Clock / 写真タグ等の原因箇所を修正
-↓
-実ユーザーで再確認
-~~~
-
-初期段階では、👍 / 👎 をそのまま自動学習や自動プロンプト変更へ接続しない。
-**人間・ソラが原因を確認してから仕様を調整する**ことで、少数の評価や誤操作によって美咲の人格・関係性設計が勝手に変化することを防ぐ。
-
-この仕組みは関係性エンジンとは別系統だが、分析時には関係レベル・感情・行動・自発文面・写真タグとの関連を見られるようにし、Misaki全体の品質改善へ使える構造を目指す。
```

```text
# Gemini provider usage telemetry

Observability only. Source handoff: `docs/GEMINI_UNIT_COST_TELEMETRY_WORK_HANDOFF.md`
at commit `ed8359319181f20cf73aec87ab75c7a1405264f2` on
`docs/relationship-v1-2-stage-growth-principles` (not yet on main when implemented).

## Recorded facts

Each physical `generateContent` attempt produces its own row in
`public.misaki_gemini_usage_telemetry`, including transient retries, timeouts and
network failures. `attempt_no` starts at 1 per generator invocation; a separate
application-level generation/Relationship retry starts another invocation and
produces additional rows, never an upsert/deduplication. Aggregate all rows for
the same opaque `request_id` to include retries and analysis in turn cost.

`model` is the requested model. `success` means HTTP `Response.ok`, not a parsed
reply, confirmed Evidence/event or a completed billable user turn. A 200 response
with malformed/blocked content can still have real provider usage. HTTP failures
can also have usage. `latency_ms` measures fetch start to HTTP headers, or to
transport rejection; it excludes retry sleep, body parsing and telemetry writes.
`occurred_at` is the attempt start time.

Counts map directly from `usageMetadata`: `promptTokenCount`,
`candidatesTokenCount`, `thoughtsTokenCount`, `totalTokenCount`, and
`cachedContentTokenCount`. Missing/invalid fields remain NULL; explicitly reported
zero remains zero. Do not reconstruct totals, assume cache/thought counts are
zero, or infer charges from network failure. Pricing and FX are separate future
versioned calculation inputs. Usage does not establish a provider invoice by
itself, and NULL rows must remain visible as coverage gaps in later cost reports.

## Identity semantics and future cohort analysis

`user_id` is the auth user UUID verified by the server for the context in which
the Gemini call occurs. It is not necessarily a permanent account or billing
account ID: anonymous authenticated user UUIDs are included. NULL means no
verified identity was supplied; it does not identify a plan or cohort.

Free / Premium cohort analysis must never infer a plan from `user_id` alone,
including whether it is present. Future analysis must safely join the verified
auth identity to canonical account and subscription information, accounting for
anonymous-to-permanent identity transitions and the subscription state applicable
at `occurred_at`. Unresolved identity or subscription mappings must remain unknown
rather than being assigned a plan by assumption. This telemetry change implements
no canonical-account mapping, subscription join, plan detection or billing logic.

## Integration and failure isolation

- Authenticated chat generation: `normal_reply`, server-verified user UUID and
  existing validated request UUID (including anonymous authenticated users).
- Permanent and anonymous canonical Relationship processing, including temporary
  import: `relationship_analyzer` / `critical_validator`, verified owner and turn
  request ID. Analyzer/validator accept an optional usage sink only; schemas,
  prompts, parsing and return values are unchanged.
- `proactive_reply`, `body_clock`, `image_generation` are reserved enum values;
  none of those runtimes or acting-lab calls are instrumented by this change.

The server-only sink registers a Next.js `after()` callback immediately. Inserts
run after the response, also when nested inside existing Relationship `after()`
work. No DB operation is awaited by Gemini, retry decisions, or a Relationship
lease. Retry-body usage is read from a clone asynchronously, bounded to 2 seconds
and 1 million characters; unreadable/late/oversized retry bodies yield NULL usage.
Telemetry DB fetches have a 2-second timeout and no application write retries.
Failed registration/insert emits only `GEMINI TELEMETRY WRITE FAILED`, never an
exception payload. Failures lose observations without altering product behavior.
This is best effort, not a durable accounting ledger.

An explicit storage allowlist includes only usage, transport facts, classification
and opaque correlation IDs. No message/reply, system prompt, memory,
Evidence/supportingTurn, raw response, key, currency or price is passed to storage.

## Database and verification

Migration: `20261004045307_gemini_usage_telemetry.sql`. Initially generated via
`supabase migration new`, then aligned with the version recorded by the remote
Supabase migration API to prevent applying the same DDL twice.

The independent table has no Relationship/quota foreign keys, triggers, RPCs or
client write route. RLS is enabled; PUBLIC/anon/authenticated privileges revoked.
Only service_role receives SELECT/INSERT; policies target that role exclusively.
Indexes support time-range, user/time and request-level cost analysis.

`tests/gemini-usage-telemetry.rollback.sql` checks service writes/reads, separate
attempt rows, NULL defaults, forbidden anon/authenticated reads/writes and PUBLIC
revocation in a transaction, leaving no synthetic data behind.

2026-10-04 DDL/advisor verification on Misaki:

- Security: no findings for the new table; existing findings were unchanged.
- Performance: only three new unused-index INFO findings, expected before
  collection/analysis starts. Keep these purposeful analysis indexes and review
  after actual workload develops. [Advisor explanation](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index).
- No production application deployment or merge is part of this Draft PR. The
  additive, empty server-only table is prepared; runtime collection starts only
  after a separately reviewed deployment.
```

```text
#!/usr/bin/env python3
"""Read-only GitHub development inventory. No branch/PR/Issue mutations."""
import datetime as dt
import json
import os
import sys
import urllib.error
import urllib.parse
import urllib.request

REPO = os.environ["GITHUB_REPOSITORY"]
TOKEN = os.environ["GITHUB_TOKEN"]
NOW = dt.datetime.now(dt.timezone.utc)
STALE_DAYS = int(os.environ.get("STALE_DAYS", "14"))
API = "https://api.github.com"

def get(path):
    req = urllib.request.Request(API + path, headers={
        "Authorization": "Bearer " + TOKEN,
        "Accept": "application/vnd.github+json",
        "X-GitHub-Api-Version": "2022-11-28",
        "User-Agent": "development-inventory-readonly",
    })
    with urllib.request.urlopen(req, timeout=30) as response:
        return json.load(response)

def pages(path):
    result = []
    page = 1
    while True:
        separator = "&" if "?" in path else "?"
        batch = get(path + separator + "per_page=100&page=" + str(page))
        if not isinstance(batch, list):
            raise RuntimeError("Unexpected API response")
        result.extend(batch)
        if len(batch) < 100:
            return result
        page += 1

def age(timestamp):
    if not timestamp:
        return None
    updated = dt.datetime.fromisoformat(timestamp.replace("Z", "+00:00"))
    return (NOW - updated).days

def main():
    repo = urllib.parse.quote(REPO, safe="/")
    metadata = get("/repos/" + repo)
    default = metadata["default_branch"]
    branches = pages("/repos/" + repo + "/branches")
    all_prs = pages("/repos/" + repo + "/pulls?state=all")
    prs = [p for p in all_prs if p["state"] == "open"]
    issues = [item for item in pages("/repos/" + repo + "/issues?state=open") if "pull_request" not in item]
    pr_heads = {p["head"]["ref"] for p in prs if p["head"]["repo"] and p["head"]["repo"]["full_name"] == REPO}
    historical_heads = {p["head"]["ref"] for p in all_prs if p["head"]["repo"] and p["head"]["repo"]["full_name"] == REPO}
    findings = []
    for branch in branches:
        name = branch["name"]
        if name == default:
            continue
        # No-PR does NOT mean unfinished. Report only as a review candidate.
        if name not in pr_heads:
            findings.append({"type": "branch_without_open_pr", "name": name,
                             "historical_pr_found": name in historical_heads,
                             "url": "https://github.com/" + REPO + "/tree/" + urllib.parse.quote(name, safe="")})
    stale_prs = [{"number": p["number"], "title": p["title"], "days": age(p["updated_at"]),
                  "url": p["html_url"]} for p in prs if age(p["updated_at"]) is not None and age(p["updated_at"]) >= STALE_DAYS]
    stale_issues = [{"number": i["number"], "title": i["title"], "days": age(i["updated_at"]),
                     "url": i["html_url"]} for i in issues if age(i["updated_at"]) is not None and age(i["updated_at"]) >= STALE_DAYS]
    report = {"repository": REPO, "generated_at": NOW.isoformat(), "default_branch": default,
              "branch_count": len(branches), "open_pr_count": len(prs),
              "open_issue_count": len(issues), "historical_pr_count": len(all_prs), "review_candidates": findings,
              "stale_prs": stale_prs, "stale_issues": stale_issues,
              "caveat": "Candidates are NOT proof of unfinished work. Compare main, merged/closed PRs, and canonical ledger before action."}
    # Stable snapshot for comparison across successful scheduled/manual runs.
    report["snapshot"] = {
        "branches": {b["name"]: b.get("commit", {}).get("sha") for b in branches},
        "prs": {str(p["number"]): {"state": ("merged" if p.get("merged_at") else p["state"]),
                                  "head": p["head"].get("sha"), "updated_at": p["updated_at"],
                                  "title": p.get("title", ""), "body": (p.get("body") or "")[:2000],
                                  "head_ref": p["head"].get("ref", "")}
                for p in all_prs},
        "issues": {str(i["number"]): {"state": "open", "updated_at": i["updated_at"]} for i in issues},
    }
    os.makedirs("inventory-output", exist_ok=True)
    with open("inventory-output/report.json", "w", encoding="utf-8") as f:
        json.dump(report, f, ensure_ascii=False, indent=2)
    summary = ["# Development inventory (read-only)", "",
               "Repository: " + REPO, "Generated (UTC): " + NOW.isoformat(), "",
               "| Metric | Count |", "|---|---:|",
               "| Branches including default | " + str(len(branches)) + " |",
               "| Open PRs | " + str(len(prs)) + " |",
               "| Open issues | " + str(len(issues)) + " |",
               "| Branches without open PR (review only) | " + str(len(findings)) + " |",
               "| Stale PRs (>= " + str(STALE_DAYS) + " days) | " + str(len(stale_prs)) + " |",
               "| Stale issues | " + str(len(stale_issues)) + " |", "",
               "**Do not mark branches unfinished or delete them based on this report.**",
               "Consult the project's canonical ledger, closed/merged PRs and main code first.", "",
               "## Stale PRs"]
    summary.extend("- [#" + str(p["number"]) + "](" + p["url"] + ") (" + str(p["days"]) + "d): " + p["title"].replace("\n", " ") for p in stale_prs)
    summary.append("\n## Stale issues")
    summary.extend("- [#" + str(i["number"]) + "](" + i["url"] + ") (" + str(i["days"]) + "d): " + i["title"].replace("\n", " ") for i in stale_issues)
    summary.append("\nBranch candidates are available in report.json artifact.")
    text = "\n".join(summary) + "\n"
    with open("inventory-output/summary.md", "w", encoding="utf-8") as f:
        f.write(text)
    with open(os.environ.get("GITHUB_STEP_SUMMARY", "/dev/null"), "a", encoding="utf-8") as f:
        f.write(text)
    print(text)

if __name__ == "__main__":
    try:
        main()
    except (urllib.error.URLError, KeyError, ValueError, RuntimeError) as error:
        print("Inventory failed: " + str(error), file=sys.stderr)
        sys.exit(1)
```
