# 開発承認ボード（美咲 × アメふる）

> **運用全体の入口**：[美咲 × アメふる 開発管理システム総覧](../DEVELOPMENT_MANAGEMENT_OVERVIEW.md)。自動棚卸し・台帳更新・承認・ソラへの引き継ぎの現状と正本へのリンクを一か所で確認できます。

## 目的
Vercelの追加プロジェクトを使わず、GitHub Pages上で2つのリポジトリの**open PR**をiPhoneからまとめて確認する。既存の開発台帳や棚卸しを置き換えない。

## 表示と操作
- GitHub公開APIから `miyazaki1016/misaki` と `miyazaki1016/emergencyalert` のopen PRを読み取り専用で取得。
- 初期画面は**「あなたの判断待ち」**。open PRのラベル `owner-decision`、`needs-owner-decision` または `user-approval-required` が明示されたものだけを表示。Draftの仕様判断依頼も表示するが、マージ可能とは扱わない。
- その他の非Draft PRは「未整理」、Draft PRは「準備中」、全件は「すべて」に分ける。未整理を自動的に承認済み・不要とは判定しない。
- 判断待ちのカードはPR本文の `### 変更概要` / `### 判断してほしいこと` / `### 推奨と理由` を抽出する。情報不足は「未記入」と明示し、AIによる推測で埋めない。
- 「GitHubで確認・マージ」からGitHubのPR画面へ移動し、ログイン済みのユーザーが差分・CI・承認条件を確認してマージする。**このダッシュボード内からの直接マージは未実装。**
- CIチェックはカードを展開した時だけ取得。GitHub APIの制限に達した場合はエラーを表示する。
- 個人アクセストークンは保存・要求しない。GitHub Pagesは公開サイトとなるので秘密情報は載せない。

## GitHub Pages公開
`.github/workflows/approval-dashboard-pages.yml` をmainへ統合後、GitHubリポジトリの **Settings → Pages → Build and deployment → Source: GitHub Actions** を設定する。以降、ダッシュボードを変更した時またはActionsの手動実行で公開できる。

想定URL（GitHub Pages有効化後。**現時点で公開確認したURLではない**）:
`https://miyazaki1016.github.io/misaki/`

## 実際にページ上で直接マージする将来拡張
GitHub Pagesは静的配信でサーバー側の機密資格情報を安全に保管できない。直接マージには認証済みのバックエンド／GitHub App・最小権限・実行前のCI/branch保護再検証・監査ログが必要。これらなしにトークンをブラウザーへ埋め込まない。

## 再実行時の注意
Pagesが未設定のまま初回デプロイに失敗した後、同じworkflow run内のdeployジョブだけを再実行すると、同名の `github-pages` アーティファクトが2つできて配信に失敗することがある。その場合は**同じジョブの再実行を繰り返さず、Actionsの「Run workflow」で新しいworkflow runを作る**。新しいrunの公開結果を確認してから利用者へURLを案内する。

## 判断依頼の登録規約（両リポジトリ共通）

オーナーに決定してほしい具体的な項目がある場合だけ、対象PRに `owner-decision` ラベルを付与し、PR本文に以下を記載する。ラベルがなければ初期画面には表示されない。

```markdown
### 変更概要
誰に何の影響があるか、専門用語を避けて説明する。

### 判断してほしいこと
選択肢AとB、各案の結果。何を決めればよいかを一問に絞る。

### 推奨と理由
推奨する選択肢、根拠、確認済みテストと残る懸念。
```

**運用上の安全境界:** このラベルは決裁が必要という印であり、合格・承認・マージ許可ではない。アプリ本体、認証、本番、DB、通知などの変更は専用PRの検証と承認を維持。ラベル・記載がないPRも「未整理」に残るため、管理から消えない。自動分類や自動マージはこの変更には含まない。

## 🔐 ダッシュボード内からのマージ（将来機能・無効）

`merge.html` はGitHub OAuth（Supabase Auth PKCE）を利用してオーナー本人を確認し、既存Supabaseプロジェクトの独立Edge Functionに依頼する**準備用UI**。GitHubの資格情報はブラウザーへ配布しない。

`merge-config.json` の `enabled` は**false**で固定。これがfalseの限り既存ダッシュボードの「直接マージ」ボタンは表示しない。既存の「GitHubで確認・マージ」ボタンは引き続き使える。

認証、本人のGithub ID、Supabase publishable key、サーバー側の最小権限GitHubトークン、Edge Functionを設定し、認証・拒否テスト・監査とOwner確認ができるまでは有効化しない。今後のコードの導入手順と防御条件は `../../services/approval-merge-edge/README.md` に記録。

バックエンド側は現段階では **docs配下のMarkdownのみ** に対象を制限し、Draft・CI失敗・重要なコード変更などは従来通りGitHubのレビューが必要。

## 担当ソラへの引き継ぎキュー（2026-11-05追加）

「ソラへの引き継ぎ」タブは、`OWNER_TRIAGE_20261104.md` の一次仕分けから生成した `handoff-queue.json` を使用する。2026-11-04時点で**35件**（美咲担当17件、アメふる担当15件、棚卸し担当3件）。オーナー判断の美咲 #101 は含まない。

GitHub公開APIでその都度取得したオープンPRと突き合わせ、**PRが閉じた案件は表示しない**。タイトル・最新head SHAは取得時の情報を使い、仕分け日時を必ず明記する。PR本文の実装完了判定や最新の対応状況を自動推論したものではない。ラベルがなくても既存棚卸し由来の引き継ぎ候補は一覧に残る。

案件ごとに「なぜ担当へ戻すか」「次にやること」「引き継ぎ指示をコピー」を提供する。コピーした指示を該当プロジェクトの**既存の担当ソラのチャット／Work**へ貼り付ける。これにより、担当にPRやブランチの所在を毎回説明せずに済む。

**重要な制約**：この画面からChatGPTの別チャットを自動起動したり、作業が実行されたことを保証したりはしない。コピー後に担当側でGitHubの最新状態を再取得して作業する。Draft・マージ禁止・送信禁止などの制約を引き継ぐ。PRクローズや自動マージは行わない。今後の仕分け更新時はこのJSONを既存の監査資料に合わせて改訂する。
