## 接続確認

Supabase管理APIのプロジェクト情報から、プロジェクト `misaki` は `ACTIVE_HEALTHY`、リージョン `ap-northeast-1`、Postgres 17.6系であることを確認した。これは**バックアップが有効である証拠ではない**。

## 公式ドキュメントで確認した仕様

- SupabaseのPro/Team/Enterpriseプランには日次バックアップがあり、FreeプランではCLIによる定期的なオフサイトエクスポートが推奨されている。
- Proは日次バックアップの直近7日、Teamは14日、Enterpriseは最大30日へのアクセスが案内されている。PITRは別途確認が必要。
- DBバックアップにはStorage APIの**オブジェクト本体は含まれない**。DBのメタデータだけではファイルを復元できない。
- 公式案内: https://supabase.com/docs/guides/platform/backups

## プロジェクト固有の未確認事項

- 契約プランと日次バックアップの実行状況。
- PITRの有効・無効、復元可能な期間。
- 実際のバックアップ一覧と直近成功時刻。
- Storageオブジェクトの別系統バックアップと復旧手段。
- Authの対象範囲、環境変数・外部サービス設定の再構築手順。
- 30日以内のバックアップ削除方針と、匿名24時間・削除済みデータ非復活の整合性。

## 次の確認手順（読み取り専用）

1. Supabase Dashboard → 対象プロジェクト → Database → Backups を開き、Scheduled / PITRの表示と直近バックアップ時刻を確認する。
2. 契約プランと保持期間を確認する。管理APIを使う場合はバックアップ一覧の**GETのみ**。復元用POSTを呼ばない。
3. Storageに実ファイルがあるか、別途保全が必要かを調査する。個人データをログ・Issue・PRへ載せない。
4. 検証環境と復元手順を承認するまでは、バックアップ実行や本番復元を行わない。
