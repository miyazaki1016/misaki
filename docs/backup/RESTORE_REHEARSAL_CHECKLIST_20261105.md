## 実行前の前提（満たさなければ停止）

- [ ] 復元先は**本番とは別プロジェクト**であり、プロジェクトID・接続先・アクセス権を二人以上で照合する。
- [ ] バックアップは暗号化され、復元担当者のみがアクセス可能。秘密鍵・接続URL・個人データをIssue/PR/CIログへ出さない。
- [ ] データ所有者、保持期限、削除受理時刻を照合できる安全な根拠がある。削除・失効の事後情報が不足する場合は、**復元を開始しない**。
- [ ] Auth、Storage、会話原本、関係性テーブルを含む復元範囲が確定している。
- [ ] 検証環境から外部メール・プッシュ通知・課金・自発配信を送らない設定が確認できている。
- [ ] 実行手順・ロールバック・作業責任者・証跡保存先をレビュー済み。

## 段階的な検証

### A. バックアップ検証
- [ ] ファイル一覧・SHA256・取得時刻・対象スキーマ/テーブル・保持期限を記録。
- [ ] `pg_restore --list` 等でアーカイブが読めることを確認。ただし読めることは復元成功を意味しない。
- [ ] DBスキーマのマイグレーション世代、拡張、RLS、関数、トリガーを比較。
- [ ] 現行 `canonical-backup.ps1` の7テーブル限定ダンプを**完全バックアップと表示しない**。

### B. 期限・削除の検証
- [ ] 匿名データは作成時刻から24時間を超えて保持・利用されない。
- [ ] 削除受理済みのデータは、バックアップ取得後の削除であっても復活しない。
- [ ] 削除・失効情報の反映に失敗した場合は**復元全体を失敗扱い**とする。
- [ ] バックアップの保存期限が30日以内の削除ポリシーに適合する。
- [ ] メール登録への移行時に失効情報が復活しない。

### C. 整合性の検証
- [ ] `auth.users` と各 `user_id` の参照整合性。
- [ ] `misaki_relationship_events` の `source_message_id` → `conversations` と `source_delivery_id` → `misaki_proactive_deliveries`。
- [ ] `misaki_relationship_episode_evidence` → episodes/evidence。
- [ ] `misaki_relationship_pattern_consumptions` → patterns。
- [ ] 会話原本と集約履歴の整合性。関係性イベント・identity・現在値のバージョン整合性。
- [ ] 処理中リース、pending、状態適用履歴について二重処理・二重反映が起きない。
- [ ] 別ユーザー・別キャラクターの情報が混入しない。RLSの実ユーザー権限で検証する。

### D. 動作・終了判定
- [ ] 検証用の匿名/メールユーザーでログイン・履歴・関係性の読み込みを確認。
- [ ] 通知・メール・外部API送信が無効のまま維持されている。
- [ ] 件数、整合性エラー、テスト結果、残余リスクを個人データなしで記録。
- [ ] 検証環境を停止・消去し、証跡の保持期限を設定。
- [ ] **本番復元は別途明示承認が必要**。本チェックリスト完了だけで自動実行しない。
